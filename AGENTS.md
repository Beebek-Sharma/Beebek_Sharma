# 9. 3D Performance Rules

3D assets can be expensive.

Always consider:

* Polygon count
* Texture resolution
* Number of materials
* Draw calls
* Lighting complexity
* Shadow rendering
* Post-processing
* Animation loops
* Device pixel ratio
* GPU limitations
* Mobile performance
* Memory usage

Prefer:

* Optimized GLB/GLTF assets
* Compressed textures where appropriate
* Lazy loading
* Suspense/loading states
* Frustum culling where useful
* Limited lights
* Limited shadows
* Low-cost materials
* Reduced DPR on mobile
* Pausing animation when off-screen
* Static fallback images where appropriate

Do not load a large 3D scene before the rest of the portfolio can become interactive.

---

# 10. 3D Responsive Behavior

* Reduce model complexity.

* Reduced motion
* Text scaling
* Touch target sizes

Do not rely on:

* Hover

Never fabricate replacement content.

Never remove factual project, experience, education, or technical information without instruction.

# 23. Horizontal Overflow

Horizontal overflow is a defect unless intentionally designed.

Check for:

* Oversized headings
* 3D canvases
* Absolute-positioned decorations
* Wide code blocks
* Long URLs
* Images
* Cards
* Navigation
* Tables
* CSS transforms

The page should not accidentally scroll horizontally.

# 24. Safe Areas and Browser UI

For mobile browsers, consider:

* Browser address bars
* Safe areas
* Dynamic viewport height
* Notches
* Rounded display corners
* Mobile keyboard

Avoid assuming `100vh` always represents the visible viewport.

Use modern viewport units such as:

* `svh`
* `lvh`
* `dvh`

where appropriate.

# 29. Dependency Rules

Do not install a mobile/responsive library merely to solve a problem CSS can solve.

Before adding a dependency:

1. Inspect existing dependencies.
2. Check native CSS capabilities.
3. Check framework capabilities.
4. Check existing components.
5. Evaluate bundle impact.
6. Evaluate maintenance cost.
7. Confirm that the dependency provides meaningful value.

Prefer the lightest reliable solution.

# 30. Development Workflow

For every responsive task:

### Phase 1 — Inspect

Inspect:

* Repository
* Package configuration
* Components
* Styles
* Breakpoints
* Assets
* Navigation
* Animation
* 3D implementation

### Phase 2 — Understand

Determine:

* Existing responsive architecture
* Existing breakpoints
* Reusable layout patterns
* Current mobile problems
* Potential desktop regressions

### Phase 3 — Plan

Determine:

* Smallest correct change
* Whether CSS is sufficient
* Whether existing components can be reused
* Mobile/tablet/desktop behavior
* Accessibility implications
* Performance implications

### Phase 4 — Implement

Implement the change without unnecessarily rewriting unrelated code.

### Phase 5 — Validate

Check:

* Build
* Type errors
* Lint
* Console errors
* Mobile layout
* Tablet layout
* Desktop layout
* Horizontal overflow
* Touch targets
* Keyboard navigation
* Reduced motion
* 3D fallback
* Performance

### Phase 6 — Review

Ask:

> Did this change actually improve the responsive experience without damaging the existing portfolio?

Then remove unnecessary complexity.
